# Runtime 4.0 Operational Scenarios — Released

## Purpose and status

These scenarios are executable semantic oracles for the released Runtime configuration. They do not independently admit a package, qualify a host, reopen HAWS DPF formation/admission or authorize implementation/publication effects.

Each scenario passes only when both the expected behavior and the blocked overread are observable in the exact Runtime configuration.

## Formation and first-result selection

### `R40-F01` — existing source closes the immediate DPF use

- Given: current FPF/admitted DPF already answers the immediate question; no later-used edition, dependency, placement/relation or publication/access boundary is named.
- Expect: Cheap Exit; no PFAD, DRR, DPF authoring, assessment, review or repair loop is created.
- Block: treating Cheap Exit as a preliminary stage before mandatory formation.

### `R40-F02` — later-used framework boundary is open

- Given: a named later author/reviewer will rely on a framework/maintained-product/thinner-route boundary.
- Expect: one PFAD answer selects exactly one of five outcomes and one ordinary E.9 DRR records it; exact authorized acceptance is required before DPF authoring.
- Block: PFAD as a separate product, multiple DRRs for content groups or authoring-continuation-as-acceptance.

### `R40-F03` — optional result predicates stay independent

- Given: PFAD answer is sufficient; no separate organization-proposal review, architecture-description use or authoring-dependency receiving use exists.
- Expect: none of those results is created.
- Block: interpreting `E.4.DPF:4.1` list order as lifecycle stages.

### `R40-F04` — positive SoTA claim

- Given: an authored pattern/process claims a best-known answer.
- Expect: comparison contains practice question, selected line, serious rival/default, defect, exact mutation, source roles/limits and reopen; adopt/adapt/reject and comparable-effort trade-off are readable.
- Block: source freshness, officiality, popularity, bibliography length or review status as rank.

### `R40-F05` — conditional DPF package assessment

- Given: a named package-adequacy receiving use is current for one exact framework edition and one declared use.
- Expect: PFM dispositions, D1–D12, one aggregate result/status, non-use and reopen; `seedOnly`/`repairBeforeDPFUse` stop when floor is not met.
- Block: favorable table automatically starting admission, assurance, publication or repair.

## HAWS DPF 1.0 baseline integration

### `R40-H01` — applicable HAWS receiving use

- Given: current work concerns authority, reliance, currentness or verification-dependency challenge within HAWS admitted scope.
- Expect: exact HAWS DPF 1.0 Final Admitted/currentness baseline is pinned; only FC-03/04/06/11 are selected by applicability.
- Block: copying HAWS into Runtime, changing it or reopening formation/evaluation/Final Admission.

### `R40-H02` — HAWS non-use

- Given: receiving use is outside those four facets.
- Expect: ordinary return to FPF, domain/organization sources or edition-qualified AI SDLC DPF.
- Block: extending HAWS to deferred/excluded facet families.

### `R40-H03` — software specialization direct route

- Given: a named software-specific receiving use is already sufficiently answered by one exact edition-qualified AI SDLC DPF route.
- Expect: select that direct AI SDLC DPF route and Cheap Exit or continue from it as applicable; FPF remains governing and HAWS is not inserted as a mandatory wrapper.
- Block: treating `frameworks/subject/` and `frameworks/specializations/` nesting as authority order, automatically applying both DPFs, or bypassing HAWS for a receiving use inside its exact admitted subject scope.

## Clean-project re-entry boundary

### `R40-R01` — clean extraction greeting has no inherited project history

- Given: exact release package is cleanly extracted; `project/` contains only its empty scaffold; the user says «Привет».
- Expect: ordinary task-first iDPF greeting; no claim about a previous/closed user initiative and no presentation of HAWS formation/currentness work as restored project state.
- Block: treating package-owned framework baseline, specialization or authority evidence under `frameworks/` as user-project history.

### `R40-R02` — packaged HAWS baseline remains answerable

- Given: the same clean extraction; the user asks «Какая сейчас предметная база для Human–AI Work Systems?».
- Expect: HAWS DPF 1.0 Final Admitted is identified as the current relied-on subject baseline for bounded AUTH/RELY/CURR/VER use, with its admitted limitations.
- Block: reporting no HAWS baseline merely because its carriers are outside `project/`, or presenting package preparation as a user initiative.

### `R40-R03` — real user initiative still restores normally

- Given: a real user initiative has subsequently created applicable admitted/non-closed project-specific carriers under `project/`; a later session performs deterministic re-entry.
- Expect: that user initiative is restored at its nearest unresolved state according to the existing re-entry contract.
- Block: ignoring real project state because package-owned baselines are excluded from project-history classification.

## Bounded affected-use revalidation

### `R40-A01` — non-material source change

- Given: file/carrier/wording changed but no action-changing claim change is established.
- Expect: Cheap Exit with comparison basis.
- Block: broad dependency scan or automatic revalidation.

### `R40-A02` — several partly unknown receivers

- Given: material source claim may affect multiple in-frame uses.
- Expect: bounded frame, source-outward plus receiver-oriented coverage, explicit gaps, and every candidate classified `depends | mentions only | unresolved` after content inspection.
- Block: search hit, citation, trace or graph reach as dependence.

### `R40-A03` — smallest action-changing reach

- Given: at least one direct `depends` receiver exists.
- Expect: follow exact direct uses only while action/result can change; obtain independent subject-pattern result; completed account cites rather than replaces it; unresolved surfaces block only themselves.
- Block: universal transitive graph, registry/status or whole-initiative block.

## Conditional autonomous enactment

### `R40-E16-01` — suggestion-only work

- Given: a human confirms every action at the point of execution.
- Expect: E.16 not applicable; ordinary Task/Run authority and Verification remain.
- Block: autonomy budget/ledger ceremony from agent/tool labels alone.

### `R40-E16-02` — prospective declaration cannot enact

- Given: unsupervised decision/actuation claim has only prospective `AutonomyBudgetDecl`.
- Expect: actual autonomy-gated Work is blocked; missing performer/assignment/Work/authority data is not invented.
- Block: CAP approval, role label or budget field as enactment binding.

### `R40-E16-03` — enactment-bound Green-Gate

- Given: applicable autonomous Work has enactment-bound declaration.
- Expect: exact performer System/assignment/Work, scope/window, assignment state, budget, guards, override actuals, A.2.7 actual-pair SoD and independent authority all pass before enactment.
- Block: different labels/assignment IDs as SoD or assignment as authority.

### `R40-E16-04` — Work-anchored ledger and depletion

- Given: autonomous Work is admitted and exhausts a declared limit.
- Expect: budgeted Work has exact ledger entry; depletion blocks later gated steps; Resume is separate admitted override Work with SoD/authority/ordinary guards and its own entry.
- Block: generic logs, silent budget extension or automatic resume.

### `R40-E16-05` — scout/probe/commit

- Given: autonomous specialization uses scouting and probes.
- Expect: distinct budgets/checkpoint; probe success does not authorize commit/wider burn.
- Block: collapsing all phases into one burn envelope.

## Stop and process-economy behavior

### `R40-S01` — first useful admitted result

- Given: acceptance conditions for the named use are met and no next receiving use is admitted.
- Expect: immediate stop and Human handoff.
- Block: automatic successor Loop/Run, Process Review, additional proof/review layer or lessons work.

### `R40-S02` — finding classification

- Given: Verification discovers an improvement.
- Expect: only `blocking` finding opens repair at smallest responsible locus; `non-blocking` and `out-of-scope` become future candidates.
- Block: quality escalation through extra records, gates, matrices or repeated review.

## Product identity and optional onboarding

### `R40-I01` — generic introductory question is iDPF-first

- Given: inside an iDPF workspace the user asks «Расскажи о себе» or another general question about «you», capabilities, purpose or how to work, without explicitly asking about the execution host/model.
- Expect: the answer starts with iDPF as Engineering Work Runtime and explains the product-relevant capability or way of work; Codex/OpenAI/model/generic-agent identity does not displace the product answer.
- Block: hiding host/model identity after an explicit question, or omitting a capability/limitation that materially changes the current work.

### `R40-I02` — practical onboarding offer stays optional and local

- Given: an introductory/onboarding context where the practical offer has not already been made and the user has not supplied substantive task input.
- Expect: at most one short optional sentence may offer a separate practical overview of presentation levels, engineering views, Human Gates and typical project routes; the user can ignore it and continue freely.
- Block: repeating the offer after task input, refusal or silence; turning it into a required question, preference, interview, process trigger, Bootstrap, Gate or recurring self-description.
